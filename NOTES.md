# Developer Notes — Architecture Decision & Phase 2 Path

> **Status (local offline edition, 2026-10-09).** TASYIIR is now sellable as a **local Windows install** per center while keeping the hosted SaaS intact; the whole difference is one variable. **Mode:** `config/tasyiir.php` + `App\Support\Mode` (`TASYIIR_MODE`, default **`local`** so a missing variable fails closed), read through `config()` only — never `env()` outside the config file, or `php artisan config:cache` would freeze the wrong edition. Routes register per edition at boot: local gets `/setup` and never `/register-center` or `/admin`; saas gets both and never `/setup` (verified by `LocalSetupTest`/`HostedSignupTest`, which had to reset `Illuminate\Support\Env`'s singleton repository by reflection — its immutable writer kept the first test class's value for the whole process, so the second class silently tested the wrong edition). **Provisioning:** the one place a tenant+owner is created is `App\Services\CenterProvisioner::provision()` — used by the local `/setup` wizard, hosted instant signup, and admin approval alike (`Tenant::provision()` is gone). `TASYIIR_SIGNUP_REQUIRES_APPROVAL=false` makes hosted signup log the owner straight in instead of queuing a request; both paths are rate-limited per IP. `App\Http\Middleware\RequireSetup` sends every GET to `/setup` until a tenant exists — it must be **prepended** to the `web` group, not appended: Laravel's middleware priority sorts `auth` before appended group middleware, so an appended version lost to `auth` and `/dashboard` redirected to `/login` on a fresh install. **Backups:** `App\Services\DatabaseBackup` uses SQLite's `VACUUM INTO` (consistent while the app is running, no file copy race), rotating 30 automatic snapshots plus 5 safety ones; `tasyiir:backup` runs it, `RunDailyBackup` triggers it lazily once a day (same pattern as `enrollments:rollover`), `start.bat` runs it on every launch, and `update.bat` before touching anything. Restore asks the owner to type **استعادة**, takes a safety snapshot first, validates the uploaded file by opening it with PDO and checking for the expected tables, then logs everyone out. The dashboard shows an owner-only banner when the newest backup is older than `TASYIIR_BACKUP_STALE_DAYS`. **Licence:** offline Ed25519 only — `App\Services\License` verifies a base64 `{p,s}` blob with `sodium_crypto_sign_verify_detached` against a public key baked into config, bound to a machine code (SHA-256 of the motherboard UUID, `XXXX-XXXX-XXXX-XXXX`), with a 14-day trial counted from the first tenant's `created_at`. No activation server, no telemetry, no outbound request of any kind. Expiry gates the modules (`licensed` middleware) but never login, the licence page, or the backup download — a client who stops paying can always get their data out. The private key lives in `tools/license-issuer/` which is excluded from the package. **Packaging:** `scripts/build-local-release.ps1` stages the app with robocopy, runs `composer install --no-dev` and `npm run build`, drops in the portable PHP runtime, and zips `release/tasyiir-local-vX.Y.Z.zip`; `scripts/local/{install,start,stop,update}.bat` plus Arabic and French client guides. Five packaging bugs that each would have broken every client install, all found by actually installing the built zip rather than reading it: (1) PHP's compiled default `variables_order=EGPCS` populates `$_ENV`, and Laravel's `ServeCommand` then filters the child environment and drops `SYSTEMROOT`, so `artisan serve` failed with "Failed to listen on 127.0.0.1:8000 (reason: ?)" — the generated `php.ini` now sets `variables_order = "GPCS"`; (2) a stale `bootstrap/cache/config.php` travelled in the zip, which both leaked the developer's `.env` to clients and made `key:generate` report "No APP_KEY variable was found" — compiled caches are now excluded and `install.bat` runs `config:clear` and verifies the key; (3) `timeout /t` aborts with "Input redirection is not supported", so every wait is `ping -n N 127.0.0.1 >nul`; (4) Arabic in a `.bat` echo is mojibake on a client console — the launchers are pure ASCII and Arabic lives only in `دليل-التثبيت.txt`, which itself went missing from the zip because PowerShell 5.1 read the BOM-less build script as ANSI and mangled the filename (script saved UTF-8 **with BOM**, guides copied by `*.txt` glob); (5) `update.bat` used `robocopy /MIR` with *relative* `/XD` paths, which robocopy does not match — it deleted the client's existing backups and would have wiped `storage/app` uploads; it is now `/E` with absolute exclusion paths, re-tested against the live install with a pre-seeded old backup and a fake upload, both intact afterwards. **Not done, deliberately:** SaaS mode untouched, no demo data in any install path, no visual change, no telemetry/online activation/billing.

> **Status (on-site install tooling, 2026-09-21).** For selling standalone copies: `php artisan app:install-center` creates the single real center + owner login on a fresh database (refuses if a tenant exists; seeds roles/permissions first if missing; `--name/--owner/--email/--password` for scripted use, prompts otherwise; validates in English since the installer, not the center, reads it). Instead of copying the create block out of `Admin\SignupRequests::approve()` as the brief's snippet did, the block moved into **`Tenant::provision(name, ownerName, email, password)`** (transaction: tenant + owner user + `Permissions::OWNER_ROLE`; `uniqueSlug()` moved to the model too) and both `approve()` and the command call it — that, not a copy, is what keeps the two from drifting. `scripts/install-center.bat` (.env → key → sqlite file → `migrate --force` → the command; exits on failure; `*.bat`/`*.ps1` forced to CRLF in `.gitattributes`) and `scripts/setup-backup-task.ps1` (daily 20:00 task copying the DB to `database/backups`, last 30 kept; folder git-ignored). Two things the brief's PowerShell needed: the file must be saved **UTF-8 with BOM and ASCII-only** — Windows PowerShell 5.1 read the BOM-less file with an em dash as ANSI and failed to parse — and the task needs `New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -StartWhenAvailable`, otherwise on a laptop (or any PC on battery) it just sits "Queued", and a PC that is off at 20:00 never backs up at all. Verified on a fresh copy of the project (no `.env`, no DB): the .bat ran every step and stopped correctly at the interactive prompt (a piped answers file isn't a keyboard for Symfony's prompts; a person typing is fine), the command created exactly one tenant/owner (role, 11 permissions, working password, zero demo rows), a second run refused, bad input was rejected, all pages returned 200 for the owner, hosted approval still works through the shared method, and the scheduled task registered, ran (result 0x0) and produced a same-size backup. Not automatable and left to the on-site checklist in SETUP.md: XAMPP vhost, Apache-as-service, firewall, static IP. Worth deciding later: an on-site install still exposes `/register-center` with nobody reviewing requests; a config switch to hide it would be a small follow-up. Nothing committed.

> **Status (French & English, 2026-09-21).** The UI is now trilingual with Arabic as default. **Mechanism:** `users.locale` (nullable), `App\Http\Middleware\SetLocale` on the whole `web` group (user's saved choice → session → `app.locale`; also sets Carbon's locale — `ar_MA` for Arabic so months stay شتنبر/غشت), `POST /settings/language` wired to real buttons on Settings → اللغة, and Laravel's JSON dictionaries `lang/fr.json` / `lang/en.json` (591 keys) keyed by the literal Arabic string, so any string not yet wrapped or translated simply shows Arabic. All three layouts emit `<html lang dir>` dynamically (`is_rtl()` helper). **What was wrapped:** every Blade view and Livewire component — text nodes, UI attributes (`placeholder`/`title`/`aria-label`/`label`/`subtitle`/`description`/`data-toast`), PHP literals in `@php`/echo/directive/bound-attribute contexts, `<script>` chart labels (via `json_encode(__())` so a French apostrophe can't break JS), Livewire `validationAttributes` (converted from properties to methods so they can call `__()`), `messages()`, toast/`addError`/`->title()` strings, and interpolated messages rewritten as placeholder keys (`'رفض طلب «:name»'`, the schedule conflict messages, `'إيرادات :month'`). **The data/UI rule, applied concretely:** stored values (`Enrollment::$status`, user/teacher/course statuses, attendance states, payment methods, expense categories, days, rooms, role and permission keys) are never translated in code; they are translated only at display time — `x-status-badge` now renders `__($label)`, `<option value="…">` keeps the Arabic value and shows `__($value)`, and `roleLabel()`, `$r->description`, `Permissions::LABELS`, `STATUS_LABELS`, Analytics/Reports labels are wrapped where echoed. Every `where('status', 'غير مؤدي')`, `Rule::in(...)`, `wire:click="markAll('حاضر')"`, tone map key and default assignment is untouched (the post-run audit lists exactly those 51 lines and nothing else). **Beyond the brief:** `ar_date()` and `Analytics::monthLabel()` are locale-aware (French/English dates and chart months); `lang/fr/{auth,validation}.php` and `lang/en/validation.php` supply framework messages and attribute names (English validation itself comes from the framework); the mobile sidebar slides from the start edge in either direction (`rtl:translate-x-full ltr:-translate-x-full`), `td.ltr-nums` uses `text-align: start`, and the nine direction-carrying chevron/arrow icons get `ltr:rotate-180`. The physical-class audit found zero `pl-/pr-/ml-/mr-/text-left/text-right/left-N/right-N` usages. `CenterSignup` lost its `#[Title]` attribute (attributes can't call `__()`) and sets the title from `render()`. **Deliberately not translated (flagged):** notification titles/bodies are *stored* Arabic text built at event time (`Notification::notify([...])`) — translating them would need key+params storage; user-entered data (teacher specialties, course levels, names) stays as entered; the guest login page follows `session('locale')` but logout invalidates the session, so it returns to Arabic until the user logs in again (a cookie would carry it — not done). Verified: `/dashboard`, `/students`, `/payments`, `/settings`, `/admin/signups` in all three languages, DB statuses and `where()` counts unchanged, `users.locale` persists across logout/login, guest pages default to `ar`/`rtl`, French validation messages, mobile drawer direction. Nothing committed.

Verified end to end in the browser: admin → `/admin`, blocked from `/dashboard`/`/students`; public signup → pending → approve → new owner logs in to an empty center and adds staff via Phase 9's Team panel; second request rejected with a visible reason and no rows created; duplicate pending email and existing-user email both rejected with a clear message; tenant owner/reception/accountant get 403 on `/admin`. > **Status (Phase 9, 2026-09-17) — roles & permissions real and enforced end-to-end; core feature list closed.** Each center's owner manages staff accounts alone, with no platform-level involvement after the center exists. **Accounts:** `users.status` (نشط/متوقف) added; `User` now uses `BelongsToTenant`, so every user query is tenant-scoped like every other business model (`TenantScope` gained a re-entrancy guard because resolving the authenticated user is itself a `User` query). Dashboard, Notifications and Settings stay open to all staff; the sidebar, dashboard quick actions and the Settings tab strip hide anything the user can't open, and a denied request renders a proper Arabic `errors/403` page in the app shell. The header/sidebar/account role label is now the real role. **Panels:** `Settings\Team` (list, create with an owner-set initial password, edit incl. optional new password, نشط/متوقف toggle — no delete; the role select never offers مدير المركز, and `tenant_id` is stamped from the creating owner, never from input) and `Settings\Roles` (three built-ins read-only with their permission chips + per-tenant custom roles: create/edit/delete-when-unused with a permission checklist). ## Why Phase 1 wasn't a real Laravel install

The original brief called for real Laravel (Blade + Livewire + Tailwind). During setup, `composer create-project laravel/laravel` and every subsequent `composer install`/`composer require` attempt failed: this sandbox's organization-level network policy blocks `packagist.org`, `repo.packagist.org`, and `getcomposer.org`. A GitHub-mirror workaround was attempted and rejected. You (the user) were offered options and explicitly chose:

> "Plain PHP/Blade mockup, drop Livewire" — skip Composer entirely, hand-build a minimal PHP router + Blade-like templating shim, use Alpine.js instead of Livewire for interactivity.

Everything in this repo follows from that decision.

## What was built instead

A small, dependency-free PHP micro-framework designed to *look and feel* like Laravel conventions so migrating to real Laravel later is mechanical, not a rewrite:

- **`App\Routing\Route`** — static `Route::get($uri, $action)->name($name)` API, `{param}` placeholders, closures or `[Class, 'method']` callables. Mirrors Laravel's `Route` facade closely enough that `routes/web.php` reads like a real Laravel routes file.
- **`App\View\BladeLite`** — a from-scratch compiler that supports the actual Blade syntax used throughout this app: `@extends`, `@section`/`@endsection`, `@yield`, `@include`, `@if`/`@elseif`/`@else`/`@endif`, `@foreach`/`@endforeach`, `@forelse`/`@empty`/`@endforelse`, `@php`/`@endphp`, `{{ }}` (escaped) and `{!! !!}` (raw) echoes, and anonymous component tags (`<x-stat-card :value="$x" />`) with isolated variable scope and named slots. Compiled templates are cached to `storage/framework/views/` and only recompiled when the source `.blade.php` file's mtime changes — the same caching model Laravel uses.
- **Alpine.js** in place of Livewire for all client-side state: dropdowns, modals, tabs, the mobile drawer, the attendance status-cycling buttons, and the notifications filter all use `x-data`/`x-on`/`x-show`/`x-model` rather than server round-trips.
- **Fully vendored, zero-CDN assets**: Tailwind CSS (compiled via the Tailwind CLI, not the Play CDN), Alpine.js, Chart.js, lucide icons (as static SVG partials), and the Cairo/IBM Plex Mono fonts are all copied from `node_modules` into `public/build/`, `public/fonts/`, and `public/icons/` by `scripts/sync-vendor-assets.mjs`. The running app makes zero network calls — this matters both for this sandbox and for demoing the app anywhere without internet access.

## What's genuinely out of scope (by design, per the original brief)

Per the brief's explicit "do not implement" list for Phase 1, none of the following exist anywhere in this codebase, even though some page UIs (forms, "add" buttons, dropdown actions) visually suggest them:

- Real authentication / sessions / password handling
- A database, migrations, or any Eloquent-style models
- Real CRUD — every "Add", "Edit", "Delete" action shows a toast and changes nothing
- Multi-tenancy / tenant isolation
- Roles & permissions enforcement
- Any HTTP API
- Payment processing integration

All data on every page comes from `app/Support/Mock/*.php`, generated deterministically (index-based cycling, not `rand()`/`time()`), so the UI is stable and reviewable across reloads.

## Migrating to real Laravel + Livewire (Phase 2)

When Composer access is available (i.e., outside this sandbox, on your own machine or CI):

1. `composer create-project laravel/laravel planzeen-v2` and `composer require livewire/livewire`.
2. Move `resources/views/**` almost as-is — the Blade syntax used here (`@extends`, `@section`, `@foreach`, `{{ }}`, component tags) is standard Blade and will parse unmodified in real Laravel. The only things to double check: anonymous component slot edge cases and any place a `@php` block relies on this repo's specific helper functions.
3. Re-implement `app/helpers.php` functions (`mad()`, `ar_date()`, `initials()`, `is_active_route()`) as either global helpers (`app/helpers.php` autoloaded via `composer.json` `"files"`) or a Blade directive/service — they're plain PHP with no framework coupling, so this is a copy-paste.
4. Replace `App\Support\Mock\*` classes with real Eloquent models + migrations (Student, Teacher, Course, Group, Enrollment, AttendanceRecord, ScheduleSlot, Payment, Expense, SalaryPayment, Notification) — the mock classes' method names and return shapes (arrays of associative arrays) were deliberately kept close to what a `Model::all()->toArray()`/resource-collection call would return, to make this swap mostly mechanical.
5. Convert the highest-interactivity pieces (attendance status-cycling, notifications filtering, the search/filter bars, modals that will need real submit handlers) to Livewire components — Alpine's `x-data` state maps fairly directly onto Livewire component public properties, and Alpine can still be layered on top of Livewire (Livewire ships with Alpine already) for purely presentational interactivity like dropdowns/tabs.
6. Add real auth (Laravel Breeze/Fortify or Jetstream), multi-tenancy (a package like `stancl/tenancy` or a simple `team_id` scoping approach), and policies/permissions (Laravel's built-in `Gate`/`Policy` or Spatie's permission package) — none of this exists yet by design.
7. Re-point `routes/web.php` at real controllers instead of closures once controllers exist.
8. `npm run build` already produces the exact same compiled Tailwind CSS / vendored JS / icons / fonts setup real Laravel expects in `public/build` — no changes needed there beyond wiring up Vite (or keeping the Tailwind CLI build if preferred) in the new project's `package.json`.
